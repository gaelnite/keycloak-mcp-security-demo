Follow the request

Choose a trace and step through the highlighted hops. Sign-in establishes a session. Each permitted Admin call triggers a fresh workload assertion and a separate exchange.

Read every step as text

Read users

  1. Discover the protected resource A request without a bearer receives HTTP 401. The WWW-Authenticate challenge points to protected-resource metadata, which identifies the MCP resource and its authorization server.
  2. Select the helpdesk grant The chooser signs in and reads verified entitlements. Helpdesk can select keycloak.users.read. The subsequent desktop authorization request includes that scope, the MCP resource and an S256 PKCE challenge.
  3. Redeem the authorization code The demo checks callback state and issuer at the registered loopback redirect. At the token endpoint, the verifier must hash to the challenge from the authorization request. The resulting access token identifies the human user and the desktop client.
  4. Invoke list_users in lab MCP verifies the desktop bearer. Discovery reflects the selected tools. The call handler independently checks the target realm, mapped entitlement and actual issued scope before consulting Cedar.
  5. Authorize this principal and tool MCP maps the verified issuer and subject to a user principal. Cedar evaluates Read on the registered list_users tool in the requested realm. Only a clean permit lets the handler continue.
  6. Obtain the user-read workload proof The registered helper requests a JWT-SVID for the user-read requester. SPIRE attests the local caller. The assertion names the workload as subject and Keycloak’s realm issuer as audience.
  7. Exchange the two credentials MCP presents the desktop bearer as subject_token and the JWT-SVID as client_assertion. It requests the realm Admin audience and user-read scope. Keycloak authenticates the requester and issues a separate bearer for the same human.
  8. Check the exchanged token and route MCP verifies the signature, subject continuity, requester, scope set, audience, lifetime and role ceiling. The private gateway calls its authorization check with the original method and URI before it forwards the request.
  9. Read and project the response Keycloak checks the delegated Admin role. MCP returns up to 50 users with ID, username and enabled state. Only the locale fixture can also expose its locale. The desktop receives the projected result.

Approve a write

  1. Request the fixture locale change A realm administrator selects keycloak.users.locale.write and calls set_user_locale for the fixed disabled user. With valid arguments and no approval, MCP returns an approval request.
  2. Verify the operator’s approval Outside the request path, an operator reviews the request and uses an isolated signer. On the second tool call MCP verifies the signature, audience, subject, realm, action, tool, fixture, locale and expiry.
  3. Spend the single attempt MCP atomically inserts the approval ID in persistent SQLite storage. A duplicate ID fails here, including after a restart. A later policy, exchange or Admin failure still spends this attempt.
  4. Evaluate the write policy The write policy sees verified approval facts in context, along with the user, tool and realm. The grant alone cannot authorize the write.
  5. Select the locale-write identity MCP requests the JWT-SVID registered for the locale-write exchange client. The read requester identities are distinct.
  6. Exchange for locale-write The subject token must authorize the write requester. The exchange produces a new Admin bearer with the write capability and kc-admin-api scopes.
  7. Constrain method, target and body MCP constructs the update from the approved locale and fixed target. The gateway admits the capability’s PUT route for that fixture. Body construction stays inside the trusted MCP process.
  8. Apply and verify separately Keycloak evaluates its own Admin permissions and applies the update. In the live check a separate read grant verifies the result. Restoring the fixture requires an independently approved write.

Scope omitted

  1. Sign in with no tool scope A helpdesk user completes login without selecting user-read. The issued token still authenticates the user. The role makes user-read eligible for a future grant.
  2. Request the read directly The session’s tool discovery omits list_users. A direct call still reaches independent request checks, so hiding a tool in the catalog is only a usability feature.
  3. Return insufficient_scope For this entitled user the scope check fails. The HTTP transport returns 403 with the required scope in its bearer challenge. The path stops before Cedar, SPIRE and token exchange.

What desktop sign-in proves

The protected-resource metadata names the authorization server. The desktop uses Proof Key for Code Exchange (PKCE), which binds a short-lived code to the client instance that started sign-in. The desktop sends its client ID, the MCP resource URI, selected scopes, state and a PKCE challenge through the browser. Keycloak redirects the code to the registered http://127.0.0.1:49446/callback. The demo client checks state to correlate the response and checks the issuer to bind it to the expected server. It redeems the code using the original verifier. With S256, Keycloak compares BASE64URL(SHA256(verifier)) with the challenge. A copied code alone cannot complete that exchange.

Consent selects a subset of what the user’s roles allow. A signed-in user can therefore have an empty tool catalog. A rotating refresh token can renew the existing desktop grant within the session limits. Adding a tool scope requires fresh authorization. PKCE protects code redemption. Subsequent MCP requests use bearer tokens and depend on TLS and careful token handling.

Which verification keys does MCP trust?

The MCP verifier accepts configured signing algorithms and reads the JWT header’s kid to select a key from the configured issuer’s HTTPS JSON Web Key Set (JWKS). An unverified issuer check can reject a token early. Grant decisions use the signature-verified claims, including issuer, subject, audience and time bounds. An unfamiliar key ID can trigger a rate-limited refresh of the cached key set. The token never selects the key server.

For the desktop client, MCP also checks the client allowlist, bearer type, mcp_roles claim and exact audience set implied by the tool scopes. The downstream verifier separately checks the Admin audience and capability requester. The SPIRE trust bundle verifies workload assertions at Keycloak. The operator public key verifies approvals at MCP. These three signing authorities have different jobs.

Two inputs to one exchange

Whose authority?

subject_token carries the user’s MCP access token. Its requester audience connects the chosen grant to one registered exchange client. Selecting user-read gives that requester a path to exchange.

Which workload?

client_assertion carries the JWT-SVID. Keycloak authenticates the confidential requester through federated-jwt. The desktop is a separate public client using its pre-registered CIMD URL.

For list_users, MCP requests scope=keycloak.users.read and the audience ending in /admin/realms/lab. It rejects a refresh token, a copy of the inbound token, a changed subject or an unexpected scope or role. Only the verified exchange bearer goes to Admin REST. An access token’s audience identifies its recipient. The gateway’s network address can differ from that audience.

How the workload earns its SPIFFE ID

  1. Attest the nodeA SPIFFE ID is a workload name within a trust domain. A SPIFFE Verifiable Identity Document (SVID) is its signed proof. SPIRE Server trusts the node CA. Its x509pop node attestor requires proof of possession of the provisioned node certificate’s private key.
  2. Identify the local processThe agent examines the process calling its Unix Workload API socket. The registration combines its Unix UID and the SHA-256 digest of the calling executable. The agent shares the workload’s PID namespace.
  3. Issue an assertionThe MCP process invokes the registered helper for the requested capability ID and issuer audience. The same MCP workload can request the three capability identities in the mcp.demo trust domain. The current user grant constrains which exchange can proceed.
  4. Verify at KeycloakKeycloak obtains signing keys from the configured SPIRE bundle over TLS. It checks the signed assertion and the requester’s configured subject binding. A new assertion can use the same signing key. Renewal and signing-key rollover are separate events.

Read the Cedar decision

The MCP server is the policy enforcement point (PEP). It calls a local Node process running Cedar WASM, the policy decision point (PDP). Here is the request shape for the helpdesk read.

Principal and action

The user principal ID is a hash of the verified issuer and subject. Two people using the same desktop client get separate principals. The action is Read.

Resource and context

The Cedar resource is Tool::"list_users". The target realm is carried by an entity in context.resource. Other context includes installed extensions, tool registration and verified approval facts.

@id("kc-read-list-users")
permit(
  principal,
  action == KeycloakMCP::Action::"Read",
  resource == KeycloakMCP::Tool::"list_users"
)
when {
  context.toolKnown
  && resource.tier == "read"
  && principal.scopes.contains(resource.requiredScope)
  && principal in context.resource.realm
  && (resource.extension == "core" || context.extensions.contains(resource.extension))
  && (!(principal is KeycloakMCP::User) || principal.roles.contains("mcp-users-read"))
};

Its when clause requires a known read tool, the required scope, membership in the target realm, the extension condition, and mcp-users-read for a user principal. Cedar requires a matching permit and gives any matching forbid precedence. Cedar can skip an erroneous policy and report diagnostics. This PEP explicitly denies a result with evaluation errors, even if another policy permitted the call.

The default PDP deadline is 500 ms. A timeout denies the call and retires the worker. A bounded restart budget allows recovery on a later request. Failure to append a configured audit record also denies dispatch. The delegated log records a decision, policy identifiers, principal and bundle hash. A permit in that log records authorization to try the operation. The downstream update can still fail.

The smallest write

Request locale→Operator signs→Consume approval→Cedar & exchange→Fixture PUT

A realm administrator may select locale-write alone. MCP asks for approval of the exact disabled fixture and one supported locale (en, de or fr). A separate, network-isolated signer holds the private key. On the second call, MCP verifies the artifact and atomically records its ID before Cedar and dispatch. Restarting MCP preserves that record. If the exchange fails, retrying requires a new approval.

The private gateway binds the exchanged capability to the original HTTP method, normalized path and allowed query. MCP constructs the update body from the approved locale and fixture ID. Keycloak applies its own backend permissions. This distinction matters because the underlying manage-users role is broader than a locale update. The implementation trusts MCP, the private gateway and Docker administrators.

Where the evidence ends

The public listener binds to host loopback. TLS terminates at the edge, which forwards to Keycloak over HTTP on a private Docker network. The setup trusts the host, volume backups, local PKI and operator. A short-lived bearer remains usable by its holder until expiry. Local verification can therefore outlive logout or a role change.

The live tests cover all three Docker profiles, including expiry and reissuance, empty grants, route restrictions, and approval replay after restart. Multi-host isolation, continuous CA rollover and full disaster recovery require separate evidence. A restored replay database and signer key must belong to the same installation. The guide describes an experimental deployment with a preview Keycloak SPIFFE feature.
